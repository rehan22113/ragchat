The Vector DB is the bridge between both phases. Phase 1 writes chunk vectors into it. Phase 2 reads from it by searching with the question vector. Both phases use the exact same embedding model — if you change the model you must re-index. LangChain connects all pieces; it is not a step itself, it is the glue.

Step 1 Chunking

  • Splits the PDF into smaller pieces
  • chunk_size=1000 — max chars per chunk
  • chunk_overlap=200 — repeated chars at edges so context isn't lost
  • Tool: RecursiveCharacterTextSplitter

Step 2 Embeddings

  • Converts text into a list of numbers (a vector)
  • Similar meaning → similar vectors → close in space
  • OpenAI: text-embedding-3-small
  • Ollama (free, local): nomic-embed-text

Step 3 Vector Database

  • Stores chunk vectors and finds nearest ones fast
  • Chroma — local, great for learning
  • FAISS — in-memory, fastest locally
  • Pinecone — cloud, for production

Step 4 Retrieval

  • Embeds the user's question → searches the vector DB
  • Returns top-K most similar chunks (default k=4)
  • MMR strategy avoids returning duplicate chunks
  • Tool: vectorstore.as_retriever()

Step 5 RAG

  • Retrieval Augmented Generation
  • Chunks injected into the prompt as context
  • LLM answers from the document, not from memory
  • Prevents hallucination — if it's not there, it says so

LLMs OpenAI vs Ollama

  • OpenAI — cloud, needs API key, costs money
  • Ollama — 100% local, free, needs good machine
  • LangChain makes swapping them trivial
  • Both used for: embedding model + chat model

Glue LangChain

  • Framework that chains every step together
  • Document — chunk of text + metadata
  • Chain — retriever → prompt → LLM → output
  • LCEL: write pipelines with the | pipe operator

📦 Key Python Packages

  • langchain — core framework
  • langchain-openai — OpenAI models
  • langchain-ollama — Ollama models
  • langchain-chroma — Chroma vector DB
  • pypdf — PDF loading
